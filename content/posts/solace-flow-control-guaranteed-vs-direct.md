## 배경

증권사 PoC/BMT에서 Solace 연동 모듈을 개발하던 중, 시세와 별개로 원장 데이터를 구독하는 요건이 추가되었습니다.

시세는 최신값만 의미가 있기 때문에 주기적으로 컨플레이션하여 넘기는 방식으로 처리했지만, 원장 데이터는 성격이 전혀 다릅니다.
한 건도 유실되어서는 안 되고, 수신한 데이터를 후단 시스템으로 넘겨 처리해야 하는데 후단의 처리 능력에는 한계가 있었습니다.
이에 원장 구독에는 초당 처리 건수를 제한하는 유량 제어가 필요했습니다.

문제는 Solace가 이런 요건에 익숙한 브로커가 아니라는 점이었습니다.
Kafka처럼 쌓아두고 꺼내 가는 구조가 아니라, 들어온 메시지를 최대한 빠르게 구독자에게 밀어주는 실시간 전달에 특화된 브로커이다 보니 "천천히 받는다"는 개념을 어디에 걸어야 할지부터 고민이 필요했습니다.

## 목표

* 원장 데이터 구독 시 초당 처리 건수(TPS)를 제한할 것
* 유량 제어로 인해 처리되지 못한 데이터는 유실 없이 보존될 것
* TPS 값은 재기동 없이 운영 중에 동적으로 변경할 수 있을 것
* 같은 모듈에서 처리 중인 시세 구독에는 영향을 주지 않을 것

## 진행 과정

### Kafka와 무엇이 다른가

처음에는 Kafka에서 하던 방식을 떠올렸습니다.

* Kafka는 컨슈머가 브로커에서 메시지를 꺼내 가는 Pull 방식임
* 컨슈머가 poll을 천천히 하면 그만큼 천천히 가져갈 뿐이고, 가져가지 않은 메시지는 브로커의 로그에 그대로 남아 있음
* 즉, 컨슈머 쪽에서 속도만 조절하면 자연스럽게 유량 제어가 되는 구조

반면 Solace는 브로커가 구독자에게 메시지를 밀어주는 Push 방식입니다.
구독자가 처리 속도를 늦춘다고 해서 브로커가 알아서 기다려주지 않기 때문에, 구독자 쪽에서 속도를 늦추면 그 사이에 밀려온 메시지가 어디에 쌓이고 어떻게 되는지를 먼저 확인해야 했습니다.

Solace의 메시지 전달 방식은 크게 Direct와 Guaranteed 두 가지로 나뉘며, 이 부분이 유량 제어 가능 여부를 가르는 핵심이었습니다.

### Direct 방식 검토

Direct 방식은 Solace의 기본이자 가장 빠른 전달 방식입니다.

* 메시지를 브로커에 저장하지 않고, 해당 토픽을 구독 중인 클라이언트에게 바로 전달함
* 구독자의 수신 확인(ACK)을 받지 않음
* 처리량과 지연 시간 면에서 가장 유리하여 시세처럼 대량의 실시간 데이터에 적합함

다만 유량 제어 관점에서 보면 문제가 있었습니다.

* 브로커는 구독자가 처리를 늦추더라도 전송을 멈추지 않음
* 구독자가 따라오지 못해 브로커 측 전송 버퍼가 가득 차면, 이후 메시지는 브로커가 버림 ( discard )
* 버려진 메시지는 다시 받을 방법이 없으며, 다음 수신 메시지의 discard indication 정도로만 유실 사실을 알 수 있음

결국 Direct 방식에서 유량 제어를 하려면 두 가지 방법밖에 없었습니다.

1. 일단 전부 받아서 클라이언트 메모리에 쌓아두고, 쌓인 것을 정해진 속도로 꺼내 처리함
2. 정해진 속도를 넘는 메시지는 버림

1번은 유입량이 처리 속도를 계속 넘어서는 순간 메모리가 끝없이 늘어나게 되며, 장애로 재기동되면 쌓여 있던 데이터는 그대로 사라집니다.
2번은 원장 데이터에는 애초에 선택지가 될 수 없었습니다.
즉, Direct 방식은 시세처럼 일부 유실이 허용되는 데이터에는 적합하지만, 유실 없는 유량 제어에는 맞지 않는 방식으로 판단했습니다.

### Guaranteed 방식 검토

Guaranteed 방식은 메시지를 브로커의 큐에 저장해 두고 전달하는 방식입니다.

* 토픽으로 발행된 메시지가 해당 토픽을 구독하는 큐에 저장됨 ( 메시지 스풀 )
* 구독자는 큐에 바인딩된 Flow를 통해 메시지를 수신함
* 구독자가 ACK를 보내야 브로커가 큐에서 해당 메시지를 삭제함
* ACK를 받지 못한 메시지는 재연결 시 다시 전달됨

유량 제어 관점에서 가장 중요한 부분은 브로커가 ACK 받지 않은 메시지를 무한정 보내지 않는다는 점이었습니다.

* Flow에는 윈도우 크기와 큐의 미확인 메시지 최대치 ( max-delivered-unacked-msgs-per-flow ) 제한이 있음
* 구독자가 ACK를 보내지 않은 메시지가 이 한도에 도달하면, 브로커는 해당 Flow로의 전송을 멈춤
* 전송되지 못한 메시지는 버려지지 않고 큐에 그대로 남아 있음
* Flow 자체를 stop, start 하여 수신을 명시적으로 멈추고 재개하는 것도 가능함

즉, 구독자가 처리 속도만큼만 ACK를 보내면 브로커도 그만큼만 메시지를 보내게 되고, 나머지는 큐에 쌓여 대기하게 됩니다.
Push 방식인 Solace에서도 Guaranteed 방식을 사용하면 Kafka와 비슷하게 처리하지 못한 메시지를 브로커 쪽에 남겨둘 수 있다는 점을 확인할 수 있었습니다.

물론 Guaranteed 방식에도 감수해야 할 부분은 있었습니다.

* 메시지를 저장하고 ACK를 주고받는 만큼 Direct 방식보다 처리량과 지연 시간 면에서 불리함
* 유량 제어로 처리가 밀리면 그만큼 큐에 메시지가 쌓이므로, 메시지 스풀 사용량과 큐 쿼터를 모니터링해야 함

다만 원장 데이터는 시세처럼 수십만 TPS가 들어오는 데이터가 아니었고, 무엇보다 유실이 없어야 했기에 Guaranteed 방식으로 가는 것이 맞다고 판단했습니다.

### 속도를 어디에서 조절할 것인가

Guaranteed 방식으로 정하고 나서, 실제로 TPS를 제한하는 지점을 어디에 둘지 따져보았습니다.

1. 비동기 콜백 안에서 대기시키는 방식

* 메시지 수신 콜백 안에서 TPS를 초과하면 잠시 대기했다가 처리하는 방식
* 구현은 가장 간단하나, Solace 클라이언트의 콜백은 내부 디스패치 스레드에서 호출되므로 콜백을 오래 붙잡고 있으면 같은 세션의 다른 구독까지 함께 멈출 수 있음
* 본 모듈은 토픽이 많아도 세션 하나로 처리하는 구조였기 때문에, 원장 유량 제어 때문에 시세 수신까지 느려질 수 있는 문제가 있었음

2. 브로커 설정만으로 제어하는 방식

* 미확인 메시지 최대치나 윈도우 크기를 작게 잡아 브로커가 한 번에 보내는 양을 줄이는 방식
* 다만 이는 한 번에 보내는 양을 제한할 뿐 초당 건수를 직접 제어하는 것이 아니며, 운영 중에 값을 바꾸기도 번거로움

3. 별도 스레드에서 정해진 속도로 꺼내 처리하는 방식

* 원장 구독은 전용 스레드에서 정해진 속도만큼만 메시지를 꺼내 처리하고, 처리가 끝난 메시지에 대해서만 ACK를 보냄
* 속도를 넘는 메시지는 ACK가 나가지 않으므로 브로커가 전송을 멈추고 큐에 남겨둠
* 시세 구독과 스레드가 분리되어 서로 영향을 주지 않음

결국 3번 방식으로 구성했습니다.
속도 제한은 토큰 버킷 방식으로 구현하여, 매초 TPS 값만큼 토큰을 채우고 토큰이 있을 때만 메시지를 처리하도록 했습니다.

```java
public class TpsLimiter {

    private volatile int tps;
    private int tokens;
    private long lastRefill = System.currentTimeMillis();

    public TpsLimiter(int tps) {
        this.tps = tps;
        this.tokens = tps;
    }

    // 운영 중 TPS 변경
    public void setTps(int tps) {
        this.tps = tps;
    }

    public synchronized void acquire() throws InterruptedException {
        while (true) {
            long now = System.currentTimeMillis();
            if (now - lastRefill >= 1000) {
                tokens = tps;
                lastRefill = now;
            }
            if (tokens > 0) {
                tokens--;
                return;
            }
            Thread.sleep(Math.max(1, 1000 - (now - lastRefill)));
        }
    }
}
```

처리 흐름은 아래와 같습니다.

1. 전용 스레드에서 토큰을 획득한 후 큐에서 메시지를 한 건 꺼냄
2. 후단으로 데이터를 넘겨 처리함
3. 처리가 정상적으로 끝난 경우에만 ACK를 보냄

### 운영 중 TPS 변경

TPS 값은 후단 시스템의 상황에 따라 조정이 필요할 수 있으므로, 재기동 없이 바꿀 수 있어야 했습니다.

* 모듈은 이미 HTTP 리슨 서비스로 받은 전문으로 발행과 구독을 제어하고 있었으므로, 같은 방식으로 TPS 변경 전문을 추가함
* 전문을 받으면 TpsLimiter의 TPS 값만 교체하며, 값은 volatile로 선언하여 다음 토큰 충전 시점부터 바로 반영되도록 함
* 구독 자체를 끊었다가 다시 맺지 않으므로, 변경 중에도 메시지 유실이나 중복 없이 속도만 바뀜

## 결과

원장 데이터 구독을 Guaranteed 방식으로 구성하고, 전용 스레드와 토큰 버킷으로 TPS를 제한하는 구조를 갖출 수 있었습니다.

* 설정한 TPS를 넘는 메시지는 ACK가 나가지 않아 브로커의 큐에 그대로 대기하며, 유실 없이 순차적으로 처리됨
* TPS 값은 HTTP 전문으로 운영 중에 즉시 변경할 수 있음
* 원장 구독이 별도 스레드에서 처리되어, 같은 세션의 시세 구독에는 영향을 주지 않음

## 회고

Solace는 처음 접했을 때 Kafka와 비슷한 메시지 브로커라고만 생각했는데, 유량 제어라는 요건 앞에서 둘의 설계 사상이 완전히 다르다는 것을 실감할 수 있었습니다.
Kafka는 컨슈머가 속도를 결정하는 구조라 유량 제어가 자연스럽지만, Solace는 브로커가 최대한 빠르게 밀어주는 것이 기본이라 "어디에 쌓아둘 것인가"부터 먼저 정해야 했습니다.

결국 핵심은 Direct와 Guaranteed의 차이를 정확히 이해하는 것이었습니다.
같은 Solace라도 Direct는 속도를 위해 유실을 감수하는 방식이고, Guaranteed는 저장과 ACK를 통해 유실을 막는 방식입니다.
유량 제어는 결국 처리하지 못한 데이터를 어딘가에 보관해야 가능한 것이므로, 그 보관을 브로커에 맡길 수 있는 Guaranteed 방식에서만 의미 있게 구현할 수 있었습니다.

또한 같은 모듈 안에서도 시세는 Direct 성격으로 최신값만, 원장은 Guaranteed로 한 건도 빠짐없이 처리하게 되면서, 데이터의 성격에 따라 전달 방식을 다르게 가져가야 한다는 점을 다시 한번 느낄 수 있었습니다.
다만 유량 제어로 처리가 밀리는 시간이 길어지면 큐에 쌓이는 양도 그만큼 늘어나는 만큼, 운영 시에는 큐의 적재량과 스풀 사용량을 함께 모니터링할 필요가 있을 것 같습니다.

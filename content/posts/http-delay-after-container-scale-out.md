## 문제 상황

프로모션으로 인한 처리량 증가에 대비하기 위해, 기존에 이중화로 운영하던 컨테이너를 1대 증설하여 삼중화로 구성한 이후 발생한 건입니다.

본 시스템은 외부 서버로 HTTP 요청을 보내는 클라이언트 역할을 하고 있으며, 삼중화 구성 이후부터 HTTP 처리 시간이 크게 늘어나는 현상이 발생했습니다.

* 기존에는 50ms 이내로 끝나던 처리가 많게는 3,000ms 가량 소요됨
* HTTP 요청이 실패하거나 오류가 발생하지는 않으며, 순수하게 처리 시간만 길어짐

처리량에 대비하려고 증설을 한 것인데 오히려 처리가 느려진 상황이었습니다.
참고로 본 이슈는 재현 없이 현장에서 바로 처리한 건이라 별도로 남겨둔 로그는 없습니다.

## 원인 분석

### 지연 구간 확인

HTTP 연결 자체에서 오류가 발생하지는 않았기 때문에, 먼저 전체 처리 시간 중 어느 구간에서 시간이 소요되는지를 확인하기로 했습니다.
이를 위해 클라이언트(본 시스템)와 서버 양측에서 TCP DUMP를 기록하여 패킷 흐름을 비교해 보았습니다.

* 클라이언트는 요청 발생 후 10ms 이내에 SYN 패킷을 전송함
* 서버 측에서 이에 대한 응답(SYN/ACK)을 내려주기까지 약 3초가 소요됨
* 세션 연결 이후의 요청 전송 및 서비스 처리 시간은 증설 이전과 동일함

즉, 늘어난 약 3초는 전부 세션을 맺는 3-way handshake 구간에서 발생하고 있었으며, 실제 서비스 처리 시간에는 변화가 없었습니다.

### 지연 주체 판단

클라이언트는 SYN을 지체 없이 전송하고 있었으므로, 이후 연결이 수립되기까지 걸린 시간은 서버 측에서 연결 요청을 받아들이는 과정에서 발생한 것으로 보입니다.

* 삼중화 구성으로 클라이언트가 늘어난 만큼, 서버로 유입되는 연결 요청도 함께 늘어나게 됨
* 그러나 서버 측에서는 이번 구조 변경 건에 대해 별다른 조치가 없었다고 함

결국 클라이언트 증설로 늘어난 연결 요청을 서버 측이 기존 설정 그대로 받아내지 못하면서, 연결 단계에서 지연이 발생한 것으로 판단했습니다.

### 약 3초라는 수치

당시에는 위 내용까지 확인한 후 서버 측에 조치를 요청했으나, 이후 다시 돌아보니 약 3초라는 수치 자체가 중요한 단서였던 것으로 보입니다.

* SYN에 대한 SYN/ACK 응답은 애플리케이션이 아닌 서버의 OS 단에서 처리하므로, 서비스 처리 속도와는 무관한 구간임
* 서버의 연결 대기 큐(backlog)가 가득 차면, OS는 새로 들어온 SYN에 응답하지 않고 그대로 버리게 됨
* 이 경우 클라이언트는 재전송 타이머에 따라 SYN을 다시 보내게 되며, Linux 기준으로 최초 SYN 이후 약 1초, 3초, 7초 시점에 재전송이 이루어짐

즉, 서버 측 backlog가 부족하여 SYN이 버려졌고 재전송 이후에야 연결이 맺어지면서 약 3초가 소요되었을 가능성이 있습니다.
당시 덤프 상에서 같은 연결에 대한 SYN 재전송 여부를 함께 확인했다면, 이 부분을 검증할 수 있었을 것으로 보입니다.

## 해결 방법

원인이 서버 측의 연결 수용에 있는 것으로 보였기에, 아래와 같이 안내했습니다.

1. 서버 측 리소스 Pool 조정

* 늘어난 연결 요청을 처리할 수 있도록 서버 측의 리소스 Pool 크기를 조정할 것을 권고함

2. 클라이언트 측 리소스 Pool 조정 가이드

* 혹시 모를 경우를 대비하여, 유사시 클라이언트 측의 리소스 Pool도 조정할 수 있도록 방법을 함께 전달함

참고로 backlog 부족이 의심되는 경우에는 서버 측에서 아래 명령으로 확인할 수 있습니다.

```bash
# listen 큐 overflow 및 SYN drop 누적 수치 ( 계속 증가한다면 backlog 부족 )
netstat -s | grep -i -E "overflow|SYNs to LISTEN"

# 서비스 포트별 현재 대기 중인 연결 수(Recv-Q)와 backlog 최대치(Send-Q)
ss -lnt
```

* 위 수치가 증가하고 있다면 OS 파라미터인 `net.core.somaxconn`, `net.ipv4.tcp_max_syn_backlog`와 함께 애플리케이션의 listen backlog 설정도 상향이 필요함
* OS 파라미터만 올려도 애플리케이션에서 지정한 backlog 값이 더 작으면 그 값이 적용되므로, 둘 다 확인해야 함

## 결과

TCP DUMP 결과를 공유한 이후에도 서버 측 담당자는 클라이언트 측의 지연이라는 입장을 유지하여, 실제 설정 변경은 이루어지지 않았습니다.
이후 같은 이슈로 추가 문의는 없었으며, 양측 간에 내부적으로 협의가 된 것으로 보입니다.

## 배운 점

이번 건은 패킷 덤프로 지연 구간을 명확하게 짚어냈음에도, 상대편을 설득하지 못한 채 마무리된 아쉬움이 남는 건입니다.

돌아보면 지연 구간을 찾은 데에서 멈추지 않고, 왜 하필 3초인지까지 한 단계 더 들어갔어야 했던 것 같습니다.
SYN 재전송 여부나 listen 큐 overflow 수치처럼 서버 측에서 직접 확인할 수 있는 근거를 함께 제시했다면, 서버 측도 납득할 수 있는 좀 더 구체적인 근거가 되었을 것입니다.

또한 클라이언트를 증설하는 작업은 우리 쪽만의 변경으로 끝나는 것이 아니라, 연계된 서버 측에도 그만큼의 부하가 더해집니다.
앞으로 증설 작업이 있다면 연계 대상 서버가 수용 가능한 연결 수까지 사전에 함께 점검해 볼 생각입니다.

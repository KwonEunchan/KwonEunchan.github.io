## 문제 상황

운영 서버에서 CPU 사용률이 100%까지 올라가는 현상이 발생했습니다.

본 시스템은 Java 6 기반으로 운영되던 AS-IS 시스템을 Java 17 기반으로 전환한 TO-BE 시스템이며, AS-IS에서는 CPU 과점유가 발생한 이력이 없었습니다.

먼저 `top` 명령으로 확인해 보니 실제로 JVM 프로세스 하나가 CPU를 100% 가까이 사용하고 있었습니다.
이에 해당 프로세스 기준으로 스레드 단위 사용률을 다시 확인해 보았습니다.

```bash
top -H -p <PID>
```

* CPU를 점유하고 있던 스레드는 업무 스레드가 아닌 `ZWorker#0`이었으며, 스레드 하나가 CPU를 약 99% 사용하고 있었음
* 그 외 업무 스레드들의 CPU 사용률은 높지 않았음

ZWorker는 ZGC 관련 스레드로 알고 있었기에, 애플리케이션 로직보다는 GC 쪽을 먼저 확인해 볼 필요가 있을 듯했습니다.

## 원인 분석

### GC 로그 확인

GC 로그를 확인해 보니 예상대로 힙 메모리를 거의 다 사용하고 있는 상태였습니다.

* GC가 수행된 이후에도 힙 사용량이 거의 줄지 않음
* GC가 끝나자마자 다음 GC가 다시 시작되는 형태로 쉬지 않고 반복되고 있었음
* 과거에 OutOfMemoryError(이하 OOM)가 발생한 이력도 있었음

이에 JVM 기동 옵션을 확인해 보니, 운영 환경임에도 힙 메모리가 최대 1GB로 설정되어 있었고 GC는 ZGC가 적용되어 있었습니다.

```text
-Xms1g -Xmx1g -XX:+UseZGC
```

### ZGC와 ZWorker

ZGC는 Java 11에서 처음 도입되어 Java 15부터 정식 기능이 된 GC로, 힙 크기와 상관없이 STW 시간을 수 ms 이하로 유지하는 것이 목표입니다.
이를 위해 객체를 Mark 하고 Relocate 하는 작업 대부분을 애플리케이션이 동작하는 중에 동시에 수행하며, 이 작업을 실제로 수행하는 스레드가 ZWorker입니다.

* ZWorker는 ZGC의 작업 스레드로, 애플리케이션 스레드와 병행하여 살아 있는 객체를 찾고 옮기는 작업을 수행함
* Java 17의 ZGC는 부하에 따라 GC 스레드 수를 동적으로 조절하며, 적은 수의 스레드부터 시작함 ( 본 건에서도 ZWorker#0 하나가 CPU를 점유하고 있었음 )
* 즉, STW를 짧게 가져가는 대신 GC 작업에 필요한 CPU를 애플리케이션과 나눠 쓰는 방식임

결국 ZGC는 짧은 STW라는 성능을 얻는 대신 CPU와 메모리를 그만큼 더 사용하는 GC이며, 애초에 수 GB ~ 수 TB 단위의 대용량 힙을 염두에 두고 만들어진 GC입니다.

### 1GB 힙에서의 ZGC

위 내용을 바탕으로 본 시스템에서 ZWorker가 CPU를 계속 점유한 이유를 아래와 같이 판단했습니다.

* Java 17의 ZGC는 세대 구분이 없어, 매 사이클마다 힙 전체의 살아 있는 객체를 대상으로 작업을 수행함 ( 세대형 ZGC는 Java 21부터 도입 )
* ZGC는 애플리케이션과 동시에 동작하는 만큼 GC 중에 새로 할당될 여유 공간이 필요하나, 1GB 힙에서는 이 여유 공간이 부족함
* 또한 ZGC는 Compressed Oops를 지원하지 않아 객체 참조가 8byte로 저장되므로, 같은 데이터라도 다른 GC 대비 힙을 더 사용하게 됨

즉, 힙이 작아 금방 차고 GC를 수행해도 확보되는 공간이 적다 보니 GC가 끝나자마자 다시 시작되는 상황이 반복되었고, 이 작업을 ZWorker가 쉬지 않고 수행하면서 CPU를 점유한 것으로 보입니다.
할당 속도를 GC가 따라가지 못하는 상황이 이어지면 결국 메모리를 확보하지 못하게 되므로, OOM 역시 같은 맥락에서 발생한 것으로 판단됩니다.

### AS-IS와의 차이

AS-IS에서는 없던 현상인 만큼 개발 수행팀에 AS-IS 설정을 확인해 보니, AS-IS 역시 힙 메모리는 1GB로 설정되어 있었다고 합니다.

* AS-IS는 Java 6 기반으로 ZGC 자체가 존재하지 않던 버전이며, 기존 세대형 GC로 동작하고 있었음
* TO-BE는 Java 17 기반으로, 기본 GC는 G1GC임에도 별도로 ZGC가 적용되어 있었음

ZGC를 적용한 명확한 사유는 확인되지 않았으나, ZGC가 성능이 좋다는 이야기가 많은 만큼 Java 17로 전환하면서 함께 적용한 것으로 보입니다.
결국 힙 크기는 AS-IS와 동일하게 가져가면서 GC만 자원을 많이 사용하는 ZGC로 바뀐 셈이며, 이로 인해 AS-IS에서는 없던 CPU 과점유가 발생한 것으로 판단됩니다.

## 해결 방법

1. 힙 메모리 증설

* OOM 이력까지 있고, 운영 환경에서 최대 힙 1GB는 그 자체로도 낮은 값이라 판단하여 4GB 정도로 증설하는 것을 제안하려 함
* 그러나 물리 서버의 메모리 여유분을 확인해 보니 약 6GB 남짓이었음
* JVM은 힙 외에도 Metaspace, 스레드 스택 등 추가로 메모리를 사용하므로, 4GB는 여유가 부족하다고 판단되어 우선 3GB로 증설하고 추이를 지켜보기로 함

```text
-Xms3g -Xmx3g
```

참고로 ZGC는 같은 물리 메모리를 여러 가상 주소에 매핑하는 방식을 사용하기 때문에, `top` 상의 RES 값이 실제 사용량보다 크게 보일 수 있습니다.
증설 이후 메모리 사용량을 확인할 때에는 이 부분을 감안하여 보는 것이 좋을 듯합니다.

2. G1GC 전환 권고

* 힙 증설로 OOM은 개선되겠지만, 근본적으로는 본 시스템 환경에 ZGC가 맞지 않다고 판단하여 G1GC로 전환할 것을 함께 권고함

```text
-Xms3g -Xmx3g -XX:+UseG1GC
```

G1GC가 더 낫다고 판단한 이유는 아래와 같습니다.

* Java 17의 기본 GC로, 수 GB 단위 힙에서는 별도 튜닝 없이도 안정적으로 동작함
* 세대 구분이 있어 금방 사라지는 객체는 Young 영역에서 적은 비용으로 정리되므로, 매번 힙 전체를 대상으로 작업하지 않음
* Compressed Oops를 사용할 수 있어 같은 힙 크기에서도 실제로 사용할 수 있는 공간이 더 넓음
* GC에 사용하는 CPU와 메모리가 ZGC보다 적어, 서버 자원 여유가 넉넉하지 않은 본 환경에 더 적합함
* STW가 ZGC보다는 길지만, 수 ms 이하의 STW가 반드시 필요한 업무가 아니라면 체감할 수준의 차이는 아닐 것으로 보임

## 결과

우선 힙 메모리를 3GB로 증설하고 CPU 사용률과 GC 추이를 지켜보기로 했으며, G1GC 전환 건은 개발 수행팀과 함께 검토할 수 있도록 공유했습니다.

증설로 OOM과 CPU 과점유는 어느 정도 개선될 것으로 예상됩니다만, 증설 이후에도 GC 직후의 힙 사용량이 계속 높게 유지된다면 메모리 누수 가능성도 있으므로 지속적으로 확인이 필요할 듯합니다.

## 배운 점

이번 건에서 CPU를 점유한 것은 업무 로직이 아닌 GC 스레드였습니다.
프로세스 단위가 아닌 스레드 단위로 CPU 사용률을 확인해 보는 것만으로도 애플리케이션 문제인지 JVM 문제인지를 빠르게 구분할 수 있었습니다.

또한 이번 건은 AS-IS와 같은 힙 크기를 그대로 가져갔음에도 GC 알고리즘만 바뀌면서 문제가 된 사례라고 생각합니다.
새로운 GC가 성능이 좋다고 해서 무조건 좋은 것은 아니며, 해당 GC가 어떤 환경을 전제로 만들어졌는지와 서버의 자원 여유까지 함께 고려해서 선택해야 할 것 같습니다.

## 문제 상황

실시간 인터페이스를 처리하는 JVM에서 OutOfMemoryError(이하 OOM)가 발생하며 약 50초 정도 프로세스가 정지되는 현상이 발생했습니다.
JVM은 IBM J9 계열이며, GC 정책은 `-Xgcpolicy:optavgpause`, 힙 메모리는 4GB로 설정되어 있었습니다.

고객사 환경 특성상 로그 반출이 어려워 처음에는 부분적인 정보로 확인할 수 있는 선에서만 분석이 가능했고, 이후 추가로 받은 파일을 토대로 최종 분석을 진행했습니다.

먼저 OOM이 발생한 시점의 힙 메모리 여유 공간은 아래와 같이 충분히 남아 있었습니다.
쓰레드 덤프와 힙 덤프를 기록하는 데에 소요되는 시간이 다른 만큼 두 덤프의 수치가 정확히 일치하지는 않습니다만, 3.6GB 이상의 여유 공간이 남아 있음을 확인할 수 있습니다.

1. OOM 발생 이후 쓰레드 덤프가 기록되었을 당시 여유 공간 => 3,909,460,582 byte ( 약 3.64GB )
2. OOM 발생 이후 힙 덤프가 기록되었을 당시 사용 중이던 공간 => 366,944,424 byte ( 약 0.34GB 사용 중으로, 남은 여유 공간은 약 3.66GB )

여유 공간이 충분히 존재함에도 OOM이 발생한다는 부분은 일반적인 현상은 아니기에, OOM 발생 직전의 GC 수행 히스토리를 확인해 보았습니다.

## 원인 분석

### GC 수행 히스토리

OOM 발생 직전 약 9분 간의 GC 로그를 4개 구간으로 나누어 보았습니다.

[ 구간 1, 2 ]

* 16,392 byte, 32,776 byte와 같이 작은 크기의 할당에 실패하여 할당 사이클(Allocation failure cycle)이 수행됨
* 실패 당시 여유 공간은 약 0.23GB, 0.32GB로 힙 메모리가 거의 가득 찬 상태였으나, GC 이후 약 3.51GB까지 늘어나며 정상 할당됨

```text
06:09:58 j9mm.133 - Allocation failure start: oldspace=250668496/4294967296 requestedbytes=16392
06:09:58 j9mm.475 - GlobalGC end: memory=3768437192/4294967296
```

[ 구간 3 ]

* 여기서부터 본격적으로 할당 실패가 자주 발생함
* 43MB ~ 87MB 크기의 할당을 시도하였으나 실패 => 여유 공간이 약 3.13GB ~ 3.51GB로 굉장히 여유로움에도 Allocation failure 발생
* 매번 할당 사이클 작업 이후에야 정상 할당됨

```text
06:15:48 j9mm.133 - Allocation failure start: oldspace=3700675032/4294967296 loa=68200200/386547712 requestedbytes=91566512
06:15:49 j9mm.133 - Allocation failure start: oldspace=3777808800/4294967296 loa=182775328/429497344 requestedbytes=91569504
06:15:49 j9mm.133 - Allocation failure start: oldspace=3776212240/4294967296 loa=223723064/472446976 requestedbytes=91569992
```

[ 구간 4 ]

* 구간 3과 마찬가지로 여유 공간이 충분함에도 할당에 실패하여 할당 사이클이 반복 수행됨
* 그러다 87MB 할당 시도에서 기록된 로그 상 최초로 Compact 작업이 수행되나, 이마저 실패함
* 최종 할당 실패 => 여유 공간이 3,927,739,296 byte ( 약 3.66GB )나 있음에도 91,331,176 byte ( 약 87MB )를 할당할 공간이 없음

```text
06:18:36 j9mm.136 - Compact start: reason=compact to meet allocation
06:18:36 j9mm.393 - Compact prevented: reason=active JNI critical regions
06:18:36 j9mm.137 - Compact end: bytesmoved=0
...
06:18:37 j9mm.136 - Compact start: reason=compact to meet allocation
06:18:37 j9mm.393 - Compact prevented: reason=active JNI critical regions
06:18:37 j9mm.137 - Compact end: bytesmoved=0
06:18:37 j9mm.475 - GlobalGC end: memory=3927739296/4294967296
06:18:37 j9mm.101 - J9AllocateIndexableObject() returning NULL! 91331176 bytes requested
```

### Compact 실패

Compact는 흩어진 메모리를 압축하여 연속된 메모리 공간을 확보하는 작업이나, 로그 상 `active JNI critical regions` 사유로 수행되지 못하고 종료되었습니다 ( bytesmoved=0 ).
JNI critical region은 네이티브 코드가 힙 메모리의 객체를 직접 참조하고 있는 구간으로, 이 구간이 끝나기 전까지는 GC가 해당 객체의 위치를 옮길 수 없습니다.
누수라기보다는 실시간 거래 프로세스가 통신 구간에서 해당 객체들을 점유하고 있었기 때문으로 예상됩니다.

이에 Native 영역을 모두 사용했다고 의심할 수도 있으나, 현재 서버 스펙상 그럴 가능성은 적고 결정적으로 아래 오류 메시지를 보면 힙 메모리 영역에서 할당에 실패한 것으로 보입니다.
Native 영역에서 할당에 실패하였다면 관련된 다른 오류 메시지가 로깅되었을 것입니다.

```text
1TISIGINFO     Dump Event "systhrow" (00040000) Detail "java/lang/OutOfMemoryError" "Java 힙 간격" received
```

결국 압축 작업에 실패하여, 여유 공간이 3.66GB나 있음에도 87MB를 할당할 연속된 공간이 없어 OOM이 발생한 것으로 보입니다.

### optavgpause 정책과 단편화

위 히스토리에서도 보셨듯이 메모리 할당에 실패한 이력이 제법 보임에도 Compact 작업이 수행된 것은 구간 4의 막바지부터입니다.
이는 현재 적용된 `-Xgcpolicy:optavgpause` 옵션이 압축 작업을 적극적으로 수행하지 않는 설정이기 때문이며, 아래는 IBM Docs 내용을 정리한 것입니다.

* optavgpause는 힙 메모리가 단편화되었을 때에 힙 영역을 압축함 ( to compact the heap if the heap becomes fragmented )
* 압축은 STW 시간 대부분을 차지하는 무거운 작업이므로, STW를 최소화하는 것이 주 목적인 optavgpause 옵션에서는 자연스레 압축을 기피하게 됨 ( 단편화가 발생하고 나서야 비로소 압축 수행 )

위 내용으로 미루어보면 로그 상에 Compact 작업이 수행된 이력 자체가 메모리 단편화가 발생했다는 근거로 볼 수 있습니다.

사실 4GB 중 3.65GB나 비어 있는데 87MB를 할당할 연속된 공간이 없다는 부분이 저도 쉽게 이해가 되지는 않았습니다.
이에 난수로 생성한 배열로 4GB 메모리를 채웠다 비우는 시뮬레이션을 직접 돌려보았는데, 대부분의 케이스에서는 87MB를 할당하기 위한 연속된 공간이 확보되었으나 종종 연속된 최대 여유 공간이 87MB에 미치지 못하는 케이스가 나왔습니다.

아래는 그중 두 케이스로, 3.65GB의 여유 공간이 있음에도 압축 이전에는 87MB를 할당하지 못하는 예시입니다.

```text
[■□□□□□□■□□□□□□□□■□□□□□□□■□□□□□□□□□■ ... ]
 ■ 사용 중인 객체   □ 여유 공간

[예시 1] 전체 여유 공간 약 3.65GB / 연속된 최대 여유 공간 약 75MB => 87MB 할당 실패
[예시 2] 전체 여유 공간 약 3.65GB / 연속된 최대 여유 공간 약 81MB => 87MB 할당 실패
```

즉, 일반적인 상황에서 발생할 위험이 크지는 않을 듯하나 확률적으로 충분히 발생할 수 있는 현상이며, 본 JVM은 9개월 간 재기동 없이 운영되었기에 단편화가 누적되기 쉬운 조건이었던 것으로 보입니다.

또한 본 시스템은 STW 시간이 오래 걸려 전문 수신에 지연이 발생했던 이력이 있었기에 STW 시간을 최소화하기 위한 정책으로 튜닝이 되어 있었고, 이번 이슈는 그 영향으로 발생한 것으로 보입니다.

### 메모리 누수 여부

OOM인 만큼 메모리 누수도 의심해 볼 수 있으나, 아래와 같은 이유로 누수로 의심되지는 않습니다.

* GC 히스토리 상의 구간 1과 구간 2에서 3GB 가량이 GC로 해소된 점 ( 실시간으로 인터페이스가 동작하고 있었음을 감안하면 대부분의 메모리가 정상적으로 해제되고 있음 )
* 장애 발생 당시 약 50초 정도 프로세스가 정지되었는데, 해당 기간 동안 메모리에 상주한 데이터를 포함해도 힙 메모리 점유량이 전체의 10% 미만으로 매우 적다는 점 ( char[] 포함한 수치 )
* 힙 덤프에 기록된 2개의 큰 객체는 전문 데이터가 아닌 JVM 자체에서 OOM 발생 내용을 기록하기 위한 데이터로 보이며, 최종적으로 OOM을 유발한 87MB 데이터 역시 애플리케이션과 무관한 로그 기록용 데이터로 예상되는 점
* 연구소 확인 결과로도 HTTP 통신 구간에서 메모리 누수를 유발할 위험이 있는 로직은 없다는 점

초기에 부분적인 정보로 유추했던 JAXB나 HTTPAsyncClient 관련 내용 역시 본 이슈에 크게 영향을 미치는 부분은 아니었으며, 누수 위험도 없는 것으로 확인되었습니다.

## 해결 방법

현재 적용된 optavgpause는 STW 시간을 고려한 정책인 만큼, 고객사에 아래와 같이 가이드를 전달했습니다.

1. 재기동 주기 단축

* GC 정책 변경이 부담된다면, 재기동 주기를 지금보다 짧게 가져가서 주기적으로 메모리 정리가 되도록 하는 것이 좋을 것 같음
* 현재 해당 JVM은 9개월 간 재기동 없이 운영되고 있었음

2. GC 정책 재검토

* 압축을 통한 메모리 최적화가 가능한 다른 정책( 예: gencon )으로 변경하는 방안도 있으나, STW 지연 이력이 있었던 만큼 변경 시 STW 시간에 대한 검증이 함께 필요함

재기동이나 GC 정책 변경이 아니더라도 메모리 단편화에 대한 대책은 별도로 마련하는 것이 좋을 듯합니다.

## 결과

여유 공간이 충분함에도 OOM이 발생한 원인은 힙 메모리 단편화로 보입니다.
optavgpause 정책 특성상 Compact 작업이 늦게 수행되었고, 그마저도 JNI critical region으로 인해 실패하면서 87MB의 연속된 공간을 확보하지 못한 것으로 정리되었습니다.
메모리 누수는 아닌 것으로 판단하였으며, 재기동 주기 및 GC 정책에 대한 가이드를 고객사에 전달했습니다.

## 배운 점

OOM이라고 해서 무조건 메모리가 부족한 것은 아니었습니다. 여유 공간이 충분하더라도 큰 객체를 할당할 연속된 공간이 없다면 OOM이 발생할 수 있었습니다.

앞으로 OOM을 분석할 때에는 힙 사용량뿐만 아니라 할당 요청 크기와 실패 시점의 여유 공간을 함께 비교하고, Compact 수행 여부와 실패 사유까지 확인해 볼 필요가 있을 것 같습니다.
또한 STW를 줄이기 위한 GC 튜닝이 다른 쪽에서는 이런 부작용으로 이어질 수 있다는 점도 함께 고려해야 할 듯합니다.

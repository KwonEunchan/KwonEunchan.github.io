## 배경

증권사 PoC/BMT 작업을 진행하던 중 Tuxedo 원장 연계 요건이 있었습니다.

Java 시스템을 메인으로 담당하고 있다 보니 그간 Tuxedo 연계는 TDomain이나 Jolt 방식으로만 진행해 왔고, 이번에도 그중 하나로 진행하면 되겠거니 했습니다.
그런데 고객사에서는 WSL(Workstation Listener) 방식으로 연동해야 한다는 요건을 주셨고, 덕분에 처음으로 세 가지 연계 방식을 놓고 비교해 볼 수 있었습니다.

## 목표

* Java 기반 시스템에서 Tuxedo 원장 서비스를 WSL 방식으로 호출할 수 있도록 연계 모듈 개발
* 들어온 전문을 원장에 tpcall로 전달하고 응답을 받아오는 중계 역할
* TPS 3만 이상의 부하에서도 안정적으로 동작할 것

## 진행 과정

### Tuxedo 연계 방식 비교

먼저 각 방식의 장단점을 정리해 보았습니다.

1. TDomain

* Tuxedo 도메인 간 게이트웨이(GWTDOMAIN)를 통해 서버 대 서버로 연결하는 방식
* 장점 => 별도의 클라이언트 라이브러리 없이 연계가 가능하며, 양방향 호출이나 트랜잭션 전파 등 도메인 간 연계 기능을 그대로 활용할 수 있음
* 단점 => 원장 측에도 도메인 설정(DMCONFIG)이 추가되어야 하므로 원장 운영 측의 변경 부담이 크고, 모든 요청이 게이트웨이 프로세스를 거치게 됨

2. Jolt

* Jolt 서버(JSL/JSH)를 통해 순수 Java 클라이언트로 원장 서비스를 호출하는 방식
* 장점 => Java만으로 개발할 수 있어 개발 난이도가 가장 낮고, 네이티브 라이브러리를 다룰 필요가 없음
* 단점 => Jolt 서버를 한 번 더 거치는 구조이며, 호출할 서비스를 Jolt 레포지토리에 별도로 등록해야 함

3. WSL ( Workstation )

* 원장 측의 WSL/WSH를 통해 Tuxedo 클라이언트 라이브러리(ATMI)로 직접 접속하는 방식
* 장점 => 원장 측은 리스너 포트만 열어주면 되므로 도메인 설정 변경이 없고, 네이티브 ATMI로 호출하는 만큼 성능상 유리함
* 단점 => Java에서 사용하려면 C로 ATMI 클라이언트를 개발하고 JNI로 감싸야 하며, 네이티브 영역에서 문제가 발생하면 JVM 전체에 영향을 줄 수 있음

### 왜 WSL이었을까

이번 요건은 TPS 3만 이상의 서비스였는데, 고객사에서는 대량 처리 서비스에는 TDomain을 열어줄 수 없다는 입장이었습니다.

처음에는 TDomain도 대량 처리가 충분히 가능한 방식이라 조금 의아했으나, 원장을 운영하는 입장에서 생각해 보면 이해가 되는 부분이 있었습니다.

* TDomain은 요청이 게이트웨이 프로세스로 모이는 구조이기에, 외부의 대량 트래픽이 들어오면 같은 게이트웨이를 사용하는 다른 연계 업무까지 영향을 받을 수 있음
* 반면 WSL은 다수의 WSH가 클라이언트 연결을 나누어 처리하고, 접속 클라이언트 수 등도 리스너 단위로 제어할 수 있어 원장 입장에서는 부하를 격리하기 수월함
* 또한 원장의 도메인 설정을 변경하는 것 자체가 운영상 부담이 큰 작업인 만큼, 외부 시스템에는 표준 클라이언트 접속 경로인 WSL만 열어주는 것이 정책상으로도 자연스러움

즉, TDomain의 성능 자체가 부족하다기보다는 원장의 안정성과 운영 정책을 고려한 판단으로 보입니다.

### C 개발과 JNI 연동

WSL 방식으로 진행하게 되면서 C로 ATMI 클라이언트를 개발하고 이를 JNI로 호출하는 구조로 진행했습니다.
C 개발은 굉장히 오랜만이라 처음에는 감을 다시 잡는 데에 시간이 제법 걸렸으나, 결국 *.so 라이브러리를 생성하고 Java에서 JNI로 호출하는 데까지 성공할 수 있었습니다.

이 과정에서 가장 시간을 많이 쓴 부분은 의외로 라이브러리 파일 이름이었습니다.

* Java에서 `System.loadLibrary("tuxedo")`와 같이 라이브러리 이름만 넘기면, JVM이 OS에 맞게 접두어와 확장자를 자동으로 붙여서 찾음
* 즉, Linux 환경에서는 `libtuxedo.so` 파일을 찾게 되므로 파일 이름 앞에 반드시 lib이 붙어 있어야 함
* 이를 모르고 lib 없이 생성한 파일을 계속 찾게 하다 보니 라이브러리를 찾지 못하는 오류가 반복됨

```java
// java.library.path 경로에서 libtuxedo.so 를 찾음
System.loadLibrary("tuxedo");

// 또는 절대 경로로 직접 지정 ( 이 경우에는 파일 이름 그대로 사용 )
System.load("/app/lib/libtuxedo.so");
```

### 안정성을 위한 구조

네이티브 영역은 JVM의 GC가 관리해 주지 않는 만큼, 메모리 누수와 연결 관리에 특히 신경을 썼습니다.

* 연계 모듈의 인스턴스는 싱글톤으로 띄우는 방식을 고수함
* 기동 및 종료 시점에 훅을 심어두어, 종료 시에는 원장 연결과 네이티브 자원을 확실히 정리하도록 하여 메모리 누수를 최대한 줄임
* 원장 연결은 요청이 들어올 때마다 맺지 않고, 기동 시점에 풀을 사전에 생성해 두고 재사용하도록 구성함

## 결과

BMT 부하 환경에서도 연계 모듈이 큰 문제 없이 잘 버텨주었으며, 성공적으로 원장 연계를 마무리할 수 있었습니다.

## 회고

Java 시스템 위주로 업무를 하다 보니 Tuxedo 연계도 Java 쪽에서 편한 방식만 바라보고 있었는데, 이번 기회에 연계 방식별 장단점과 원장을 운영하는 입장에서의 고려 사항까지 함께 고민해 볼 수 있었습니다.

오랜만의 C 개발과 JNI 연동은 쉽지 않았지만, 라이브러리 이름 규칙처럼 막상 겪어보지 않으면 알기 어려운 부분들을 직접 부딪히며 익힐 수 있었습니다.
또한 네이티브 자원을 다루는 만큼 인스턴스 관리나 자원 정리 시점을 처음부터 설계해 두는 것이 중요하다는 점도 다시 한번 확인할 수 있었습니다.

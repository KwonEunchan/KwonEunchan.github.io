## 배경

증권사 PoC/BMT 작업을 진행하던 중 Tuxedo 원장 연계 요건이 있었습니다.

Java 시스템을 메인으로 담당하고 있다 보니 그간 Tuxedo 연계는 TDomain이나 Jolt 방식으로만 진행해 왔습니다.
다만 이번 요건은 TPS 3만 이상의 대량 처리 서비스였고, BMT인 만큼 무엇보다 성능이 잘 나와야 했습니다.
이에 익숙한 방식을 그대로 가져가기보다는 TDomain, Jolt, WSL 세 가지 연계 방식을 놓고 비교해 본 후 결정하기로 했습니다.

## 목표

* 연계 방식별 특징을 비교하여 TPS 3만 이상의 요건에 맞는 방식 선정
* 들어온 전문을 원장에 tpcall로 전달하고 응답을 받아오는 중계 역할
* 네이티브 영역을 사용하더라도 부하 상황에서 JVM이 안정적으로 동작할 것

## 진행 과정

### Tuxedo 연계 방식 비교

먼저 각 방식의 장단점을 정리해 보았습니다.

1. TDomain

* Tuxedo 도메인 간 게이트웨이(GWTDOMAIN)를 통해 서버 대 서버로 연결하는 방식
* 장점 => 별도의 클라이언트 라이브러리 없이 연계가 가능하며, 양방향 호출이나 트랜잭션 전파 등 도메인 간 연계 기능을 그대로 활용할 수 있음
* 단점 => 원장 측에도 도메인 설정(DMCONFIG)이 추가되어야 하며, 모든 요청이 게이트웨이 프로세스를 거치므로 대량 처리 시 해당 구간이 병목이 될 수 있음

2. Jolt

* Jolt 서버(JSL/JSH)를 통해 순수 Java 클라이언트로 원장 서비스를 호출하는 방식
* 장점 => Java만으로 개발할 수 있어 개발 난이도가 가장 낮고, 네이티브 라이브러리를 다룰 필요가 없음
* 단점 => Jolt 서버를 한 번 더 거치는 구조이며, 호출할 서비스를 Jolt 레포지토리에 별도로 등록해야 함

3. WSL ( Workstation )

* 원장 측의 WSL/WSH를 통해 Tuxedo 클라이언트 라이브러리(ATMI)로 직접 접속하는 방식
* 장점 => 원장 측은 리스너 포트만 열어주면 되므로 도메인 설정 변경이 없고, 네이티브 ATMI로 호출하는 만큼 성능상 가장 유리함
* 단점 => Java에서 사용하려면 C로 ATMI 클라이언트를 개발하고 JNI로 감싸야 하며, 네이티브 영역에서 문제가 발생하면 JVM 전체에 영향을 줄 수 있음

### WSL 방식 선택

개발 편의성만 보면 Jolt가 가장 좋았으나, 이번 요건에서 가장 중요한 것은 성능이었습니다.

* TDomain과 Jolt는 요청이 게이트웨이 또는 Jolt 서버를 한 번 더 거치는 구조이므로, 대량 처리 시 중간 구간이 병목이 될 수 있음
* WSL은 클라이언트가 ATMI로 WSH에 직접 접속하므로 중간 구간이 가장 적고, 다수의 WSH가 연결을 나누어 처리하여 부하가 한 곳에 몰리지 않음
* 원장 측에서도 리스너 포트만 열어주면 되므로, 도메인 설정 변경과 같은 운영 부담이 없음

반면 C로 ATMI 클라이언트를 직접 개발해야 하고, 무엇보다 네이티브 영역에서 문제가 생기면 JVM 전체가 내려갈 수 있다는 위험이 있었습니다.
이에 개발 부담과 안정성 위험은 구조적으로 보완하기로 하고, 성능상 가장 유리한 WSL 방식으로 진행했습니다.

### C 개발과 JNI 연동

WSL 방식으로 진행하게 되면서 C로 ATMI 클라이언트를 개발하고 이를 JNI로 호출하는 구조로 진행했습니다.
C 개발은 굉장히 오랜만이라 처음에는 감을 다시 잡는 데에 시간이 제법 걸렸으나, 결국 *.so 라이브러리를 생성하고 Java에서 JNI로 호출하는 데까지 성공할 수 있었습니다.

이 과정에서 가장 시간을 많이 쓴 부분은 의외로 라이브러리 파일 이름이었습니다.

* Java에서 `System.loadLibrary("tuxedo")`와 같이 라이브러리 이름만 넘기면, JVM이 OS에 맞게 접두어와 확장자를 자동으로 붙여서 찾음
* 즉, Linux 환경에서는 `libtuxedo.so` 파일을 찾게 되므로 파일 이름 앞에 반드시 lib이 붙어 있어야 함
* 이를 모르고 lib 없이 생성한 파일을 계속 찾게 하다 보니 라이브러리를 찾지 못하는 오류가 반복됨

```java
// java.library.path 경로에서 libtuxedo.so 를 찾음
System.loadLibrary("tuxedo");

// 또는 절대 경로로 직접 지정 ( 이 경우에는 파일 이름 그대로 사용 )
System.load("/app/lib/libtuxedo.so");
```

### WSH Connection Pool

WSL 방식에서 가장 신경 쓴 부분은 크래시 위험이었습니다.
JNI로 호출하는 네이티브 코드에서 오류가 발생하면 Java 예외로 잡히지 않고, JVM 프로세스 자체가 비정상 종료될 수 있기 때문입니다.

특히 요청마다 원장에 접속하고 끊는 방식( tpinit / tpterm )으로 구현하게 되면, TPS 3만의 부하에서 네이티브 영역의 연결 생성과 해제가 쉴 새 없이 반복됩니다.
그만큼 네이티브 자원을 할당하고 해제하는 구간이 늘어나, 누수나 크래시가 발생할 여지도 커지게 됩니다.

이에 WSH와의 연결을 미리 만들어 두고 재사용하는 Connection Pool 구조로 구성했습니다.

* 기동 시점에 정해진 수만큼 WSH 연결을 미리 생성해 둠
* 요청이 들어오면 Pool에서 연결을 빌려 tpcall을 수행하고, 응답을 받은 후 다시 반납함
* 연결 생성과 해제는 기동, 종료 시점에만 일어나므로 부하 구간에서는 네이티브 자원을 새로 할당하는 일이 거의 없음
* Pool 크기만큼만 네이티브 호출이 동시에 일어나므로, 요청이 몰리더라도 네이티브 영역으로 들어가는 동시 호출 수가 제한됨
* 오류가 발생한 연결은 Pool에서 제외하고 새로 맺어 교체하여, 문제가 생긴 연결이 계속 재사용되지 않도록 함

Pool을 포함한 연계 모듈의 인스턴스는 싱글톤으로 관리했으며, 기동 및 종료 시점에 훅을 심어두어 종료 시에는 Pool에 있는 원장 연결과 네이티브 자원을 확실히 정리하도록 했습니다.
네이티브 영역은 JVM의 GC가 관리해 주지 않는 만큼, 정리 시점을 놓치면 그대로 누수로 이어지기 때문입니다.

## 결과

BMT 부하 환경에서도 연계 모듈이 큰 문제 없이 잘 버텨주었으며, 성공적으로 원장 연계를 마무리할 수 있었습니다.

## 회고

Java 시스템 위주로 업무를 하다 보니 Tuxedo 연계도 그간 익숙한 TDomain이나 Jolt만 사용해 왔는데, 이번에는 성능 요건을 기준으로 세 가지 방식을 직접 비교해 보고 선택할 수 있었습니다.

WSL은 성능상 가장 유리한 대신 네이티브 영역을 직접 다뤄야 하는 부담이 있었고, 결국 방식을 고르는 것보다 고른 방식의 약점을 어떻게 보완할지가 더 중요했던 것 같습니다.
이번에는 Connection Pool로 연결 생성과 해제를 기동, 종료 시점으로 몰아두면서 부하 구간에서의 크래시 위험을 줄일 수 있었습니다.

오랜만의 C 개발과 JNI 연동은 쉽지 않았지만, 라이브러리 이름 규칙처럼 막상 겪어보지 않으면 알기 어려운 부분들을 직접 부딪히며 익힐 수 있었습니다.

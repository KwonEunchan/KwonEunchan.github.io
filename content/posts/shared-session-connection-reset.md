## 문제 상황

연계된 두 시스템에서 서로 상대편이 연결을 끊었다는 로그가 동시에 발생하는 현상이 있었습니다.
편의상 두 시스템을 시스템A, 시스템B로 표현하겠습니다.

* 시스템A와 시스템B의 로그 모두에서 `Connection reset by peer` 확인
* 즉, 양쪽 모두 상대편이 먼저 연결을 끊었다고 기록하고 있는 상황

어느 한쪽이 먼저 끊었다면 반대편에만 reset이 기록되어야 하는 만큼, 양쪽 모두에 같은 로그가 찍혀 있다는 부분이 쉽게 이해되지 않았습니다.

다만 운영 환경이라 세션 접속 정보 등의 상세 로그가 남아 있지 않았고, 이미 지나간 현상이라 덤프도 확보할 수 없어 남아 있는 로그만으로 분석을 진행해야 했습니다.

## 원인 분석

### 연계 구조 확인

먼저 두 시스템 간의 연계 구조를 확인해 보니, 일반적인 요청마다 연결을 맺고 끊는 방식이 아니었습니다.

* 두 시스템은 하나의 세션을 연결해 둔 상태로 계속 유지함
* 여러 서비스가 해당 세션 하나를 함께 사용하여 모든 전문을 송수신함

즉, 세션 하나에 문제가 생기면 그 세션을 사용하던 모든 서비스가 함께 영향을 받는 구조였습니다.

### 현상 발생 시점의 로그 비교

세션 관련 로그가 없는 만큼, 양쪽 시스템의 서비스 로그를 시간 순으로 맞춰가며 reset 직전에 어떤 처리가 있었는지 확인했습니다.

* reset이 기록되기 직전, 한쪽 시스템에서 특정 전문의 데이터 값 문제로 처리에 실패한 이력이 있음
* 해당 서비스는 처리 실패 시 Exception을 발생시키며 사용 중이던 세션을 종료하도록 되어 있었음
* 이후 같은 세션을 사용하던 다른 서비스들에서도 연쇄적으로 세션 종료 처리가 발생함

위 흐름을 정리하면 아래와 같습니다.

1. 한쪽 시스템의 서비스가 데이터 값 문제로 처리에 실패하며 Exception과 함께 세션을 종료함 => 상대편 시스템에 `Connection reset by peer` 기록
2. 같은 세션을 사용하던 다른 서비스들이 세션 종료를 감지하고 연쇄적으로 세션 종료 처리를 수행함 => 반대편 시스템에도 `Connection reset by peer` 기록

결국 한 서비스의 예외 처리로 시작된 세션 종료가, 세션을 공유하던 다른 서비스들의 종료 처리로 이어지면서 양쪽 모두에 reset 로그가 남은 것으로 보입니다.
네트워크 장비나 OS 레벨의 문제라기보다는, 하나의 세션을 공유하는 구조에서 서비스 단위의 예외가 세션 단위의 종료로 이어진 것이 근본적인 원인으로 판단됩니다.

## 해결 방법

본 현상은 특정 전문의 데이터 값 문제에서 시작되었으나, 같은 상황은 언제든 다시 발생할 수 있으므로 아래와 같이 개선 방안을 안내했습니다.

1. 예외 처리 범위 조정

* 개별 전문의 처리 실패는 해당 전문에 대한 오류 응답으로만 처리하고, 공유 중인 세션까지 종료하지 않도록 예외 처리 범위를 조정할 것을 권고함

2. 세션 공유 구조 검토

* 모든 서비스가 세션 하나를 공유하는 구조에서는 한 서비스의 문제가 전체로 번질 수 있으므로, 업무 단위로 세션을 분리하거나 세션 풀 방식으로 구성하는 방안도 함께 검토가 필요함

3. 재발 대비 로그 확보

* 재발 시 원인을 빠르게 추적할 수 있도록 세션 연결 및 종료 시점과 종료 주체를 남기는 로그를 운영 환경에서도 확보해 둘 것을 권장함

## 결과

양쪽 시스템 모두에 기록된 `Connection reset by peer`는 한 서비스의 예외 처리로 인한 세션 종료와, 이에 따른 다른 서비스들의 연쇄 종료로 발생한 것으로 정리되었습니다.
예외 처리 범위 조정 및 세션 구조 검토, 로그 확보 방안을 고객사에 전달했습니다.

## 배운 점

이번 건은 기술적으로 복잡한 현상이라기보다는, 분석에 필요한 정보가 없다는 점이 가장 힘들었습니다.
운영 환경이라 세션 정보 로그가 없었고 이미 지난 현상이라 덤프도 없었기에, 결국 남아 있는 서비스 로그의 시간을 하나하나 맞춰가며 흐름을 재구성할 수밖에 없었습니다.

양쪽 모두 상대가 끊었다고 기록하는 경우에는 어느 한쪽이 틀린 것이 아니라, 이번처럼 종료가 연쇄적으로 일어났을 가능성도 함께 염두에 두어야 할 것 같습니다.
또한 문제가 터진 뒤에는 확보할 수 있는 정보가 한정적인 만큼, 운영 환경이라도 최소한의 세션 로그는 평소에 남겨두는 것이 중요하다는 점을 다시 한번 느낄 수 있었습니다.

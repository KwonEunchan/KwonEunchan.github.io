## 문제 상황

연계 솔루션이 동작 중인 JVM에서 GC로 인해 서비스가 30초 이상 지연되는 현상이 발생했습니다.
JVM은 Java 8 기반의 IBM J9 계열이며, 힙 메모리는 4GB로 설정되어 있었습니다.

본 시스템은 총 3대의 서버(이하 서버#1 ~ #3)로 구성되어 있으며, 3대 모두 동일한 솔루션이 설치되어 동일한 서비스를 제공하고 있습니다.
다만 서버#3은 서버#1, #2보다 Java 마이너 버전이 상대적으로 높은 상태였습니다.

GC 로그를 확인해 보니 대부분의 GC는 200ms 내외로 처리가 되었으나, 아래 두 케이스만 이례적으로 긴 시간이 걸렸습니다.

* 서버#1 => 32,185.677ms ( 09:01:42 ~ 09:02:14 )
* 서버#2 => 30,503.771ms ( 09:05:25 ~ 09:05:56 )

반면 같은 리소스가 배포되고 같은 트래픽을 받은 서버#3에서는 해당 현상이 발생하지 않았습니다.

## 원인 분석

### ClassUnload 구간에서의 지연

서버#1에서 발생한 GC 기준으로 살펴보면, 사이클은 09:01:42.708 ~ 09:02:14.918로 총 32,210ms가 소요되었으나 그중 31,412ms 가량이 ClassUnload 구간에서 소요되었습니다.

```text
// GC 사이클 시작 ( Free 용량 : 1% )
<cycle-start id="946271" type="global" timestamp="2026-07-09T09:01:42.708" intervalms="109192.611" />
<gc-start id="946272" type="global" timestamp="2026-07-09T09:01:42.710">
  <mem-info free="42950656" total="4294967296" percent="1">
    <mem type="soa" free="0" total="4252016640" percent="0" />
    <mem type="loa" free="42950656" total="42950656" percent="100" />
  </mem-info>
</gc-start>

// JVM 메모리 상에서 Live 객체 식별 ( 약 174ms )
<gc-op id="946274" type="mark" timems="173.803" timestamp="2026-07-09T09:01:42.884" />

// 클래스 언로딩 ( 약 31.4초, 81개의 클래스 로더와 149개의 클래스를 언로딩 )
<gc-op id="946275" type="classunload" timems="31412.326" timestamp="2026-07-09T09:02:14.297">
  <classunload-info classloadercandidates="666" classloadersunloaded="81" classesunloaded="149"
    setupms="10.343" scanms="31401.862" postms="0.120" />
</gc-op>

// 메모리 회수 ( 약 3ms )
<gc-op id="946276" type="sweep" timems="2.999" timestamp="2026-07-09T09:02:14.300" />
<gc-end id="946277" type="global" durationms="32185.677" timestamp="2026-07-09T09:02:14.896">
  <mem-info free="3959182536" total="4294967296" percent="92" />
</gc-end>

// 사이클 종료
<cycle-end id="946279" type="global" timestamp="2026-07-09T09:02:14.918" />
```

* Mark 약 174ms, Sweep 약 3ms로 일반적인 GC 작업 자체는 평소와 다를 바 없이 빠르게 처리됨
* ClassUnload 31,412ms 중 31,401ms가 scan 단계에서 소요됨 ( 666개의 클래스 로더 후보를 검사하여 81개의 클래스 로더, 149개의 클래스를 해제 )
* GC 이후 여유 공간은 1% => 92%로 정상 회수됨

ClassUnload 구간에서는 더 이상 참조되지 않는 클래스와 이를 로드했던 클래스 로더들을 메모리에서 해제하는 작업을 수행합니다.
해제된 클래스 수 자체는 많지 않으나, 해제 여부를 판단하기 위해 후보 클래스 로더들을 검사하는 데에 대부분의 시간이 소요된 것으로 보입니다.

### 구버전 클래스가 남아 있던 이유

당일 07시 경에 신규 리소스를 배포하고 호출 테스트를 진행했던 이력이 있었습니다.
리소스를 재배포하게 되면 JVM 메모리 상에는 해당 리소스의 구버전과 신버전에 대한 클래스 및 클래스 로더가 각각 공존하게 됩니다.

이후 09시 경에 트래픽이 이전 대비 폭증하면서 메모리 여유 공간이 1% 미만이 되었고, 공간 확보를 위해 구버전 클래스 및 클래스 로더를 해제하고자 ClassUnload가 발생한 것으로 보입니다.

문제 발생 이전에도 주기적으로 GC가 발생하긴 하였으나 ClassUnload가 발생한 건은 드물었으며, 종종 발생한 건에서는 소량만 해제되어 비교적 빠르게 완료된 것을 확인할 수 있었습니다.

즉, 리소스 배포 이후 JVM 메모리 상에 구버전과 신버전의 클래스 및 클래스 로더가 일시적으로 공존하였고, 이후 GC 과정에서 구버전 클래스에 대한 해제 작업이 한꺼번에 수행되면서 지연이 발생한 것으로 판단됩니다.
이는 JVM의 자연적인 메모리 정리 과정에서 발생한 현상으로, 특정 리소스의 설정 오류나 비정상 동작에 의해 발생한 장애로 보이지는 않습니다.

### Java 마이너 버전에 따른 차이

다만 위 내용만으로는 동일한 조건이었던 서버#3에서 현상이 발생하지 않은 부분이 설명되지 않습니다.

GC의 세부 동작 및 ClassUnload 처리 방식은 Java 8의 마이너 버전에 따라 일부 차이가 있을 수 있습니다.
3대의 서버 모두 동일한 솔루션과 서비스, 동일한 배포 이력을 가지고 있었던 만큼 유일한 차이는 Java 마이너 버전이었으며, 상대적으로 높은 버전의 서버#3에서만 현상이 발생하지 않은 점을 감안하면 해당 버전에서는 ClassUnload 처리가 개선된 것으로 보입니다.

## 해결 방법

ClassUnload 작업은 정리 대상이 많거나 대상의 참조 관계가 복잡한 경우 처리 시간이 증가할 수 있습니다.
본 현상의 재발이 우려된다면 아래와 같은 방법으로 예방할 수 있도록 고객사에 안내했습니다.

1. 배포 이후 순차 재기동

* 리소스 배포 이후에는 트래픽을 제어한 후 순차적으로 컨테이너를 재기동하여, 구버전 클래스 및 클래스 로더가 메모리에 남지 않도록 함

2. Java 마이너 버전 업그레이드

* 서버#1, #2의 Java 마이너 버전을 서버#3과 동일한 수준으로 업그레이드할 것을 권고함
* 서버#3이 이미 동일한 솔루션과 서비스를 해당 버전으로 운영하고 있는 만큼, 현 서비스 동작에 영향이 없다는 점은 사실상 검증이 된 셈임

## 결과

장기 지연의 원인은 배포 이후 남아 있던 구버전 클래스 및 클래스 로더의 ClassUnload 작업으로 정리되었으며, 리소스 자체의 문제는 아닌 것으로 결론 내렸습니다.
재발 방지를 위해 배포 이후 순차 재기동 가이드와 함께, 서버#3 기준으로 Java 마이너 버전 업그레이드를 고객사에 안내했습니다.

## 배운 점

GC 지연이라고 하면 보통 Mark나 Compact 단계를 먼저 의심하게 되는데, 이번처럼 ClassUnload 단계 하나에서 대부분의 시간이 소요되는 경우도 있었습니다.

앞으로 GC 지연을 분석할 때에는 전체 소요 시간만 보지 않고 단계별 소요 시간까지 나누어 확인해 볼 필요가 있을 것 같습니다.
또한 재배포는 서비스 중단 없이 진행할 수 있다는 장점이 있지만, 그만큼 구버전 클래스가 메모리에 남게 된다는 점을 운영 관점에서 함께 고려해야 할 듯합니다.

마지막으로 동일한 구성의 서버가 여러 대 있는 환경이라면, 정상인 서버와 비교하는 것만으로도 원인을 좁히거나 조치 방안을 검증하는 데에 큰 도움이 된다는 점도 다시 한번 느낄 수 있었습니다.

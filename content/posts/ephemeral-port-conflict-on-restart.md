## 문제 상황

시스템 정기 재기동 작업 중 JVM 하나가 정상적으로 기동되지 않는 현상이 발생했습니다.
편의상 기동에 실패한 JVM을 JVM#1, 같은 도메인의 다른 멤버들을 JVM#2, JVM#3으로 표현하겠습니다.

배포나 설정 변경 없이 단순 재기동만 진행한 상황이었기에 기동 로그를 확인해 보니, JVM#1에 배포된 애플리케이션이 LISTEN 해야 할 포트 하나가 이미 점유 중이라 기동되지 못한 이력을 확인할 수 있었습니다.

해당 포트를 점유한 프로세스는 같은 장비의 JVM#2였습니다만, JVM#2는 이번 작업 대상도 아니었고 배포 이력도 없었기에 갑자기 해당 포트를 점유할 이유가 없었습니다.

어차피 작업 간 서비스는 점검 명목으로 막아둔 상태였으므로, 급하게 복구하기보다는 원인 분석을 먼저 진행할 필요가 있을 듯하여 추가로 확인을 진행했습니다.

## 원인 분석

먼저 점유 중인 포트의 상태를 확인해 보니 LISTEN이 아닌 ESTABLISHED 상태였습니다.
즉, JVM#2가 서비스 용도로 해당 포트를 bind 한 것이 아니라 외부로 나가는 세션의 로컬 포트로 사용하고 있었던 것으로 보입니다.

이에 TCP 덤프를 떠서 해당 포트의 패킷을 확인해 보니 상대편은 또 다른 JVM인 JVM#3이었으며, 주고받는 전문은 도메인 내부 멤버 JVM 간의 헬스체크 전문임을 확인할 수 있었습니다.

결국 JVM#2가 JVM#3과 헬스체크 세션을 맺으면서 OS로부터 할당받은 에페메럴 포트가 하필 JVM#1의 서비스 포트와 겹친 상황이었습니다.

* 클라이언트 측 세션의 로컬 포트는 애플리케이션에서 따로 지정하지 않으면 OS가 에페메럴 포트 범위 내에서 임의로 할당함 ( Linux 기본값 32768 ~ 60999 )
* OS는 이미 LISTEN 중인 포트를 에페메럴 포트로 할당하지는 않으나, 재기동으로 JVM#1이 내려가 있는 동안에는 해당 포트가 비어 있으므로 할당 대상이 될 수 있음
* 위 구간에 JVM#2의 헬스체크 세션이 새로 맺어지면서 해당 포트를 가져간 것으로 보이며, 헬스체크 세션은 장시간 유지되는 연결이기에 JVM#1이 기동을 시도하는 시점까지 계속 점유하고 있었던 것으로 판단됨

위 내용으로 미루어보면 근본적인 원인은 서비스 포트가 에페메럴 포트 범위 안에 포함되어 있었다는 점으로 보입니다.
재기동 시점과 세션 생성 시점이 겹쳐야만 발생하는 만큼, 평소에는 드러나지 않다가 간헐적으로 발생할 수 있는 유형입니다.

## 해결 방법

당장의 현상은 단순 재기동으로 해소가 될 수 있었습니다.
다만 같은 상황이 언제든 반복될 수 있으므로, 서비스 포트와 에페메럴 포트 범위가 겹치지 않도록 아래와 같이 OS 파라미터 조정 가이드를 고객사에 전달했습니다.

1. 에페메럴 포트 범위를 서비스 포트 대역 밖으로 조정

* `net.ipv4.ip_local_port_range` 값을 서비스 포트를 포함하지 않는 대역으로 변경 ( 예: 서비스 포트가 모두 40000 미만이라면 `40000 60999` )
* 범위를 좁히는 만큼 동시에 맺을 수 있는 아웃바운드 세션 수도 줄어들기 때문에, TIME_WAIT가 많은 환경이라면 여유 있게 잡는 것이 좋음

2. 서비스 포트를 에페메럴 포트 할당 대상에서 제외

* `net.ipv4.ip_local_reserved_ports`에 서비스 포트를 등록
* 등록된 포트는 에페메럴 포트로 할당되지 않으며, 애플리케이션에서 명시적으로 bind 하는 것은 그대로 가능함
* 범위 자체를 건드리지 않아도 되므로 서비스 포트가 범위 중간에 흩어져 있는 경우에 적합함

두 설정 모두 `/etc/sysctl.conf` 또는 `/etc/sysctl.d/` 하위 설정 파일에 등록한 후 `sysctl -p`로 반영하면 되며, 재부팅 없이 즉시 적용되고 이미 맺어진 세션에는 영향이 없습니다.

```text
# /etc/sysctl.d/99-port.conf
net.ipv4.ip_local_port_range = 40000 60999
net.ipv4.ip_local_reserved_ports = 38080,38090-38099
```

## 결과

재기동 이후 JVM#1은 정상적으로 기동되었습니다.
OS 파라미터 조정이 적용되면 동일한 현상은 재발하지 않을 것으로 예상됩니다만, 신규 서비스 포트가 추가될 때마다 위 설정과 겹치지 않는지는 지속적으로 확인이 필요할 듯합니다.

## 배운 점

포트 충돌이라고 하면 보통 같은 포트를 LISTEN 하려는 프로세스가 두 개인 경우를 먼저 떠올리게 되는데, 이번처럼 다른 프로세스의 아웃바운드 세션이 서비스 포트를 가져가는 경우도 있을 수 있었습니다.

앞으로 'Address already in use'를 마주하게 된다면 점유 중인 프로세스뿐만 아니라 해당 소켓의 상태가 LISTEN인지 ESTABLISHED인지부터 확인해 볼 필요가 있을 것 같습니다.

## 배경

증권사 BMT에서 주식 시세 정보를 받아 클라이언트 단말로 전달하는 시나리오를 수행했습니다.

시세는 UDP로 유입되는데, 우리가 평소 주식 화면을 볼 때를 떠올려 보면 시세가 내려오는 거래소도 다르고 종목마다 가격도 제각각입니다.
즉, 수신한 시세를 모든 단말에 그대로 뿌리는 것이 아니라 단말이 원하는 정보( 거래소 구분, 종목코드 등 )에 맞춰 골라서 내려줘야 하는 구조였습니다.
게다가 그 조건은 단말마다 모두 다를 수밖에 없습니다.

이번 글에서는 전달 방식을 선정한 과정과 함께, 실제 BMT를 수행하면서 부딪혔던 부분과 수신 구간 튜닝, 그리고 유실 점검 방법 위주로 정리해 보려고 합니다.

## 목표

* UDP로 유입되는 시세를 수신 구간에서 최대한 유실 없이 받을 것
* 단말별로 서로 다른 필터 조건( 거래소, 종목코드 )을 적용하여 필요한 시세만 전달
* 바이트와 문자열이 혼재된 전문을 전부 해석하지 않고 필요한 값만 빠르게 추출
* 유실 발생 여부를 OS 레벨에서 수치로 확인할 수 있을 것

## 진행 과정

### 전달 방식 선정 ( UDP vs TCP 비동기 vs 웹소켓 )

단말로 전달하는 방식은 UDP, TCP 비동기, 웹소켓 세 가지를 놓고 검토했습니다.
판단 기준은 이번 요건의 핵심인 "단말마다 다른 조건으로 구독한다"를 얼마나 자연스럽게 담을 수 있는가였습니다.

| 구분 | UDP | TCP 비동기 | 웹소켓 |
| --- | --- | --- | --- |
| 전송 신뢰성 | 유실 감수 | 보장 | 보장 ( TCP 기반 ) |
| 메시지 경계 | 데이터그램 단위로 보장 | 없음 ( 직접 프레이밍 필요 ) | 프레임 단위로 보장 |
| 구독 조건 전달 | 연결 개념이 없어 별도 채널 필요 | 제어 메시지 규약 직접 설계 | 같은 연결에서 양방향으로 처리 |
| 연결 상태 확인 | 불가 | 직접 구현 | ping/pong 표준 제공 |
| 방화벽, 기존 인프라 | NAT, 방화벽 구간 통과가 까다로움 | 별도 포트 정책 필요 | HTTP 포트 기반, WebtoB 등 기존 인프라 활용 가능 |
| 오버헤드 | 가장 적음 | 적음 | 프레임 헤더 2~14 byte, 핸드셰이크는 최초 1회 |

1. UDP

* 장점 => 가장 가볍고 지연이 적음
* 단점 => 수신 구간뿐만 아니라 단말 구간에서도 유실을 감수해야 하며, 단말이 원하는 조건을 서버에 알려줄 연결 상태 자체가 없음

2. TCP 비동기

* 장점 => 신뢰성이 보장되면서도 프로토콜 오버헤드가 적음
* 단점 => 메시지 경계와 구독, 해지, 조건 변경 규약을 모두 직접 정의해야 하므로 결국 자체 프로토콜을 하나 만드는 셈이 됨

3. 웹소켓

* 장점 => 단말이 연결 후 원하는 거래소나 종목코드를 보내면, 서버는 해당 세션에 필터 조건을 매핑해 두기만 하면 됨
* 장점 => 단말이 중간에 조건을 바꾸더라도 재연결 없이 같은 연결로 처리 가능
* 단점 => 프레임 헤더가 추가되나, 지속 전송 구간에서의 부담은 크지 않은 수준

TCP 비동기로 진행하더라도 결국 웹소켓이 이미 제공하는 기능( 프레이밍, 양방향 제어, 연결 상태 확인 )을 다시 만들어야 하는 상황이었기에, 구독 상태를 연결 단위로 자연스럽게 들고 갈 수 있는 웹소켓으로 진행했습니다.

### 바이트와 문자열이 섞인 전문 처리

전문은 고정 길이였지만 바이너리 숫자 필드와 문자열 필드가 섞여 있어 처음에는 다소 까다로웠습니다.

다만 시세를 내려주는 것이 목적이다 보니, 중계 서버에서 모든 바이트를 해석할 필요는 없었습니다.
필터링의 기준이 되는 값( 거래소 구분, 종목코드 등 )만 알면 나머지는 단말에서 사용할 정보이므로 원본 바이트 그대로 넘겨주면 충분했습니다.

이에 전문 레이아웃에서 필요한 필드의 오프셋과 길이만 확인하여 해당 위치만 잘라서 읽는 방식으로 진행했습니다.

```java
// 필요한 구분값만 오프셋 기준으로 추출
byte pbid = buf.get(PBID_OFFSET);

byte[] code = new byte[CODE_LEN];
buf.get(CODE_OFFSET, code);   // Java 13+ absolute bulk get
String stockCode = new String(code, StandardCharsets.US_ASCII);
```

### 엔디안 문제

숫자형 필드를 읽어보니 값이 생각했던 것과 많이 다르게 나왔습니다.
확인해 보니 Java는 빅 엔디안이 기본인데, 시세를 내려주는 쪽은 C로 작성된 것인지 리틀 엔디안으로 값을 보내고 있었습니다.

예를 들어 리틀 엔디안으로 `70000`을 보내면 `70 11 01 00` 순서로 들어오는데, 이를 빅 엔디안으로 읽으면 `1,880,162,560`이 됩니다.

다행히 값이 워낙 크게 틀어져서 금방 눈치챘지만, 그렇지 않았다면 꽤 헤맸을 것 같습니다.
조치는 버퍼의 바이트 순서만 리틀 엔디안으로 지정해 주면 되었습니다.

```java
ByteBuffer buf = ByteBuffer.wrap(packet, 0, len).order(ByteOrder.LITTLE_ENDIAN);
int value = buf.getInt(FIELD_OFFSET);
```

참고로 함께 확인한 주의점은 아래와 같습니다.

* 1 byte 필드나 ASCII 문자열 필드는 엔디안의 영향을 받지 않으며, 2 byte 이상의 숫자형 필드( short, int, long )만 영향을 받음
* `slice()`나 `duplicate()`로 만든 버퍼는 원본의 `order` 설정을 이어받지 않고 다시 빅 엔디안으로 돌아가므로, 파생 버퍼를 만들 때마다 `order`를 다시 지정해야 함

### OS 파라미터 튜닝

UDP는 애플리케이션이 소켓 수신 버퍼에서 데이터를 꺼내가는 속도보다 유입 속도가 빠르면, 버퍼가 가득 찬 시점부터 커널이 그대로 패킷을 버립니다.
대량 시세가 순간적으로 몰리는 구간을 버티기 위해 아래 커널 파라미터를 조정했습니다.

```bash
# /etc/sysctl.d/99-udp-quote.conf
net.core.rmem_max = 268435456          # 소켓 수신 버퍼 최대값 ( 256MB )
net.core.rmem_default = 33554432       # 소켓 수신 버퍼 기본값 ( 32MB )
net.core.netdev_max_backlog = 250000   # NIC -> 커널 처리 대기 큐 길이
net.ipv4.udp_mem = 4194304 8388608 16777216   # UDP 전체 메모리 한도 ( page 단위 )

sysctl -p /etc/sysctl.d/99-udp-quote.conf
```

* `rmem_max` => 애플리케이션에서 `SO_RCVBUF`를 크게 요청하더라도 이 값을 넘을 수 없으므로 반드시 함께 올려야 함
* `rmem_default` => 소켓 생성 시 별도 지정이 없을 때 적용되는 기본 수신 버퍼
* `netdev_max_backlog` => NIC에서 올라온 패킷이 커널에서 처리되기 전 대기하는 큐로, 순간 유입이 몰릴 때 여기서 먼저 버려질 수 있음
* `udp_mem` => 시스템 전체 UDP 소켓이 사용할 수 있는 메모리 한도로, 버퍼를 크게 잡아도 이 한도에 걸리면 수신이 막힘

애플리케이션에서도 수신 버퍼를 명시적으로 요청하고, 실제로 반영된 값을 기동 로그로 남겨 확인했습니다.
`rmem_max`보다 크게 요청하면 에러 없이 조용히 잘리기 때문에 반드시 반영값을 확인하는 것이 좋습니다.

```java
DatagramChannel ch = DatagramChannel.open();
ch.setOption(StandardSocketOptions.SO_RCVBUF, 64 * 1024 * 1024);
log.info("SO_RCVBUF applied = {}", ch.getOption(StandardSocketOptions.SO_RCVBUF));
```

튜닝 전에는 부하 구간마다 `RcvbufErrors` 카운터가 계속 증가했는데, 튜닝 이후에는 동일한 부하에서 증가가 멈춘 것을 확인할 수 있었습니다.

### UDP 유실 점검

UDP는 애초에 유실을 감수하는 프로토콜이다 보니, "유실이 났는지"와 "어디서 났는지"를 확인할 수 있어야 합니다.
OS에서 UDP 데이터그램 입출력 통계를 아래 명령으로 확인할 수 있습니다.

```bash
# UDP 통계 요약
netstat -su

# 동일 정보 ( 누적 카운터 원본 )
cat /proc/net/snmp | grep Udp

# 직전 호출 대비 증가분만 확인 ( 부하 전후 비교에 편리 )
nstat -az | grep -i udp
```

주로 본 항목은 아래와 같습니다.

* `InDatagrams` => 애플리케이션 소켓까지 정상 전달된 데이터그램 수
* `NoPorts` => 수신 포트에서 리슨 중인 소켓이 없어 버려진 수
* `InErrors` => 수신 중 오류로 버려진 전체 수
* `RcvbufErrors` => 소켓 수신 버퍼가 가득 차서 버려진 수 ( 애플리케이션 처리 속도 부족의 신호 )
* `OutDatagrams`, `SndbufErrors` => 송신 건수와 송신 버퍼 부족으로 실패한 수

이 밖에 구간별로 유실 위치를 좁힐 때는 아래 명령도 함께 확인했습니다.

```bash
# 소켓별 버퍼 사용량과 drop 수 ( skmem의 d 값 )
ss -uamn

# NIC 단 drop 확인
ethtool -S eth0 | grep -i -E "drop|miss"

# netdev_max_backlog 초과로 버려진 수 ( 각 행의 두 번째 컬럼, 16진수 )
cat /proc/net/softnet_stat
```

정리하면 NIC 단 drop은 `ethtool`, 커널 대기 큐 초과는 `softnet_stat`, 소켓 버퍼 초과는 `RcvbufErrors`로 구간을 나누어 볼 수 있습니다.
BMT 중에는 부하 전후로 `nstat`을 찍어 증가분을 비교하는 방식으로 유실 여부를 확인했습니다.

### Vector, Logstash 검토

처음에는 수신한 UDP를 MCI 솔루션으로 넘기기 전에, 앞단에 별도 파이프라인 도구를 두는 방안을 준비했습니다.
모든 패킷을 MCI가 그대로 받게 되면 MCI 쪽 성능이 나오지 않을 수 있다고 보았기에, 앞단 파이프라인에서 걸러낼 것은 걸러내고 유효한 데이터만 MCI로 넘기려는 의도였습니다.
이를 위해 Vector와 Logstash를 준비해 두었습니다.
최종적으로는 사용하지 않았지만, 검토한 내용을 간략히 남겨둡니다.

1. Vector

* Rust로 작성된 경량 데이터 파이프라인 도구로, Datadog에서 오픈소스로 관리하고 있음
* source( 수집 ) => transform( 가공 ) => sink( 전달 ) 구조이며, `socket` source로 UDP 수신이 가능함
* VRL( Vector Remap Language )로 필터와 변환 로직을 작성할 수 있음
* 단일 바이너리에 메모리 사용량이 작아, 같은 서버에 붙여 두기에 부담이 적음

2. Logstash

* Elastic Stack의 데이터 수집, 가공 도구로 JVM 기반으로 동작함
* input => filter => output 구조이며, `udp` input 플러그인으로 수신이 가능함
* grok, mutate 등 플러그인 생태계가 풍부하고 Elasticsearch 연동이 가장 자연스러움
* 반면 JVM 기반이라 기본 메모리 사용량이 크고, 대량 처리 시 별도 힙 튜닝이 필요함

그런데 실제로 부하를 넣어보니 MCI 솔루션의 성능이 생각보다 잘 나왔습니다.
앞단에서 걸러주지 않아도 MCI가 유입되는 패킷을 모두 받아낼 수 있었기에, 굳이 파이프라인을 두어 HOP을 늘릴 필요가 없다고 판단했습니다.

* 구간이 하나 늘어나면 그만큼 지연이 추가되고, 버퍼링 지점 즉 유실이 발생할 수 있는 지점도 하나 더 늘어남
* 장애 발생 시 확인해야 할 대상도 함께 늘어나므로, 운영 측면에서도 구간은 적을수록 유리함

이에 최종적으로는 Vector와 Logstash 없이 UDP 수신부터 MCI까지 바로 연결하는 구조로 진행했습니다.
다만 이후 유입량이 크게 늘어 MCI 앞단에서 물량을 덜어줘야 하는 상황이 오거나, 시세를 Kafka나 Elasticsearch 등으로 별도 적재해야 하는 요건이 생긴다면 이때는 가벼운 Vector를 우선적으로 고려해 볼 생각입니다.

## 결과

* 단말별로 거래소, 종목코드 조건을 받아 필요한 시세만 웹소켓으로 전달하는 시나리오를 BMT에서 정상 수행함
* 필터 기준이 되는 값만 오프셋으로 잘라 읽으면서 전문 전체를 해석하지 않고도 필터링이 가능했음
* 리틀 엔디안 필드를 바이트 순서 지정으로 바로잡아 숫자형 값을 정상적으로 해석함
* OS 파라미터 튜닝 이후 동일 부하에서 `RcvbufErrors` 증가가 멈추었고, 유실 여부를 OS 카운터로 확인할 수 있는 점검 절차도 함께 마련함
* MCI가 전체 유입량을 감당하는 것을 확인하여, 앞단 파이프라인( Vector, Logstash ) 없이 HOP을 최소화한 구조로 마무리함

## 회고

평소 Java만 다루다 보면 바이트 순서를 신경 쓸 일이 거의 없는데, C로 작성된 시스템과 바이너리로 주고받으니 바로 차이가 드러났습니다.
이번에는 값이 크게 틀어져서 금방 알아챘지만, 앞으로 바이너리 전문을 다룰 때는 레이아웃과 함께 송신 측 바이트 순서부터 확인하려고 합니다.

또한 UDP는 유실을 감수하는 프로토콜이지만, 감수한다는 것이 확인하지 않아도 된다는 의미는 아니라는 점도 다시 느꼈습니다.
`RcvbufErrors` 같은 카운터를 미리 보는 습관만 있어도 "애플리케이션이 느린 건지, 네트워크에서 빠진 건지"를 훨씬 빠르게 구분할 수 있었습니다.

마지막으로 Vector나 Logstash처럼 좋은 도구를 준비해 두었더라도, 실제 측정 결과 필요하지 않다면 과감히 빼는 것도 하나의 판단이라는 점을 배웠습니다.
성능을 걱정해 미리 구간을 추가하기보다 먼저 측정해 보고 판단하는 것이 맞았고, 구간을 하나 줄이는 것이 곧 유실 지점과 장애 지점을 하나 줄이는 일이기도 했습니다.

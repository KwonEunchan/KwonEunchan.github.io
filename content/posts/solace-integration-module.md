## 배경

증권사 PoC/BMT 작업 중 Solace 메시지 브로커와의 연동 요건이 있었습니다.

시세 정보를 Solace로부터 지속적으로 구독하여 화면 쪽에 웹소켓으로 전달하고, 반대로 전문을 받아 Solace로 발행하는 역할까지 연계 솔루션에서 처리해야 하는 구조였습니다.
연동에는 고객사에서 제공하는 Solace 연동용 클라이언트 라이브러리를 사용해야 했는데, 공개된 라이브러리가 아니다 보니 참고할 자료가 거의 없어 라이브러리 자체를 파악하는 것부터 시작해야 했습니다.

## 목표

* 연계 솔루션의 HTTP 리슨 서비스로 받은 전문을 통해 Solace 발행과 구독을 제어
   * 토픽 + 데이터 => 해당 토픽으로 발행
   * 토픽 + 큐 => 구독 생성 또는 기존 구독 재사용
* 구독한 시세 및 체결 정보를 웹소켓으로 전달
* 구독 기준 최대 TPS 40만 수준의 시세 데이터 수신
* 발행 기준 TPS 3만 이상 처리
* 토픽이 동적으로 생성, 제거되더라도 자원 누수가 없을 것

## 진행 과정

### 모듈 구성

연계 솔루션에서는 import 하여 사용하기만 하면 되도록, 발행과 구독 기능을 jar 하나(fat jar)로 묶어 별도 모듈로 구성했습니다.
연계 솔루션 쪽에서는 HTTP로 들어온 전문을 해석하여 모듈의 발행 또는 구독 메서드를 호출하는 역할만 하도록 하여, Solace 연동 로직과 업무 로직이 섞이지 않도록 했습니다.

### 세션 관리 구조

처음에는 토픽 + 큐 조합마다 클라이언트 서비스 인스턴스를 하나씩 만들어 맵으로 관리하는 방식을 구상했습니다.
다만 이 방식은 토픽이 늘어날수록 세션과 내부 스레드도 함께 늘어나게 되고, 토픽이 제거될 때 인스턴스 정리가 누락되면 그대로 누수로 이어질 위험이 있었습니다.

이에 아래와 같이 구조를 변경했습니다.

* 발행용과 구독용으로 클래스를 나누고, 각각 클라이언트 서비스 인스턴스 하나만 쥐고 있는 싱글톤으로 구성함
* 구독은 토픽이 아무리 많아도 세션 하나에서 토픽을 추가, 제거하는 방식으로 처리함
* 싱글톤은 Holder 방식으로 구현하여, 별도의 동기화 없이도 최초 사용 시점에 한 번만 생성되도록 함
* 기동 및 종료 시점에는 JEUS lifecycle에 훅을 걸어, 종료 시 세션과 구독을 확실히 정리하도록 함

```java
public final class SolaceSub {

    private SolaceSub() { }

    private static class Holder {
        private static final SolaceSub INSTANCE = new SolaceSub();
    }

    public static SolaceSub getInstance() {
        return Holder.INSTANCE;
    }
}
```

세션을 하나로 가져가면서 토픽 수와 관계없이 자원 사용량이 일정하게 유지되었고, 정리해야 할 대상도 명확해져 누수 관리가 훨씬 수월해졌습니다.

### 구독 현황 관리

구독이 동적으로 생성, 제거되다 보니 현재 어떤 토픽이 어떤 큐로 구독되고 있는지를 따로 관리할 필요가 있었습니다.
이에 구독 현황을 Oracle 테이블로 관리하도록 했습니다.

* GWID, 토픽명, 큐명을 PK로 두고 구독 상태와 변경일을 함께 기록함
* 구독 생성, 제거 시점마다 상태를 갱신하여, 모듈 바깥에서도 현재 구독 현황을 확인할 수 있도록 함

### 웹소켓 전달 방식

이번 요건에서 가장 고민이 많았던 부분은 구독한 데이터를 웹소켓으로 전달하는 부분이었습니다.
Solace로부터 수신되는 시세 데이터가 최대 TPS 40만 수준이었는데, 이를 그대로 웹소켓으로 넘기게 되면 서버뿐만 아니라 수신하는 화면 쪽에서도 감당하기 어려운 수준이었습니다.

물론 체결 정보는 당연히 한 건도 빠짐없이 전달되어야 합니다.
다만 시세의 경우에는 굳이 40만 TPS를 전부 넘길 필요는 없다고 판단했습니다. 화면에서 시세를 보는 것은 결국 사람인 만큼, 사람이 인지할 수 있는 속도 이상으로 갱신해 보아도 의미가 없기 때문입니다.

이에 데이터 성격에 따라 아래와 같이 전달 방식을 나누었습니다.

* 시세 => 주기적으로 종목별 최신값만 전달 ( 컨플레이션 )
   * 수신한 시세는 종목별로 최신값만 유지하고, 사람이 인지할 수 있는 수준의 주기마다 모아서 전달함
   * 주기 사이에 들어온 중간값은 최신값으로 덮어쓰이므로, 수신량이 아무리 많아도 전송량은 종목 수와 주기에 의해서만 결정됨
* 체결 => 빠짐없이 전부 전달
   * 체결은 한 건이라도 빠지면 안 되므로 버리지 않되, 건마다 보내지 않고 묶어서 전송하여 메시지 수를 줄임

## 결과

발행과 구독 기능을 jar 하나로 구성하여 연계 솔루션에 탑재했으며, 토픽이 동적으로 생성, 제거되는 상황에서도 세션은 하나로 유지되는 구조를 갖출 수 있었습니다.
또한 구독 현황을 테이블로 관리하면서 운영 중에도 구독 상태를 쉽게 파악할 수 있게 되었습니다.

특히 시세를 주기적으로 컨플레이션하여 전달하면서, 최대 TPS 40만 수준의 시세 수신량과 관계없이 웹소켓 전송량을 일정하게 유지할 수 있었습니다.

## 회고

처음 접하는 메시지 브로커에, 공개되지 않은 라이브러리까지 다뤄야 했던 만큼 초반에는 라이브러리 동작을 파악하는 데에 시간이 제법 걸렸습니다.

그 과정에서 처음 구상했던 토픽별 인스턴스 방식을 그대로 진행했다면 토픽이 늘어날수록 자원 관리가 어려워졌을 것 같습니다.
기능을 먼저 만들기보다 세션과 자원의 생명주기를 어떻게 가져갈지부터 정해두는 것이 장기적으로 운영하기에 훨씬 수월하다는 점을 다시 한번 느낄 수 있었습니다.

또한 TPS 40만이라는 수치 앞에서 처음에는 어떻게 다 넘길지부터 고민했는데, 결국 데이터를 실제로 소비하는 쪽이 무엇을 필요로 하는지를 먼저 생각해 보는 것이 답이었습니다.
같은 구독 데이터라도 시세와 체결처럼 성격에 따라 전달 방식을 다르게 가져가야 한다는 점은, 실시간 데이터를 다루며 새롭게 고민해 볼 수 있었던 부분이었습니다.
